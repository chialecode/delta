# Git 初始化、阶段提交与 amend

## 初始历史

用户要求首个提交只包含 **零字节 README.md**，第二个提交保存文档框架，之后单独保存技术比较与首轮计划。本次另授权清理第二提交中的已撤回技术方案并重写后续计划提交；第一个提交保持不变。无需再次初始化仓库。

默认本地 main，实施使用相容任务分支。Git 身份复用环境有效身份，不伪造作者。后续不自行重写已经结束的其他阶段；用户新授权优先。

## 一个阶段一个可审核提交

用户 D-09 明确要求：一个阶段尽可能只保留一个 commit；Agent B 的实现、Agent A 的审核修正和 B 的返工**直接 amend 该阶段提交**，不把错误实现、逐问题修复或沟通轮次保存为独立提交。阶段是计划中声明的交付单元，不等于每个 W 工作包；R1 的 W00～W11 为一个实现阶段。

A 在文档框架之后建立当前阶段提交，起初保存该阶段计划。B 将实现直接 amend 进这个阶段提交，A 审核修正与 B 返工继续沿用；R1 第三个提交从计划演进到最终实现，不另建第四个实现提交。不得 amend 文档框架提交。同阶段使用 `git commit --amend --no-edit` 或更新成描述最终状态的消息。阶段关闭且开始下一阶段后，新建下一阶段 commit。需要纠正已关闭阶段时，先确定受影响下游和当前授权，不能误 amend 另一阶段。

日常保存依靠工作区与本地备份；确有 checkpoint 提交时，在交付前合并回该阶段一个 commit。默认不创建 fixup/返工提交留在最终分支历史。报告保留 F 编号、错误触发、修复说明和验证事实；精简 Git 历史不等于伪造当时通过或删除审查证据。

## amend 前后与交接

1. 检查当前分支、HEAD、工作区归属和阶段父提交，确认 HEAD 就是当前阶段提交；尚无该阶段提交时才正常 commit；已有该阶段计划提交则 amend。
2. 比较交接的旧 SHA 与现场新 SHA/树差异，保留对方已完成修改；不能因 amend 导致 SHA 变化就退回旧版本。默认同一工作区单写入者。
3. 只暂存归属明确的本阶段文件；运行受影响检查和 `git diff --check`，核对 `git diff --cached --stat`，避免 `git add .` 混入他人文件。
4. amend 后检查父提交不变、阶段提交数量符合计划、工作区剩余改动归属明确。最终消息必须给出**新的完整 SHA**和对方 prompt；旧 SHA 失效，使用更新后的 prompt。
5. 报告记录稳定的阶段 ID、计划版本、阶段父提交、测试源码指纹、F 问题处理及证据；最终包含报告本身的 SHA 在消息中给出，避免反复自引用 amend。被测内容变化后补必要验证，不能把旧 SHA 的测试无条件套到新树。

当前授权覆盖本地阶段历史整理与阶段计划/实现/审核合并，无需每轮询问是否 amend。若存在未知下游、他人分支依赖或同时写入，先核对并隔离，不覆盖他人工作。已经发布的历史不能仅凭本规则强推；push、PR、合并、tag、发布及强推均按用户对具体外部动作的已有授权执行。

未选择项目许可证不阻塞本地开发；对外分发前处理集中台账。历史重写前可保存忽略目录下的恢复包；恢复包不是当前交付历史，不对外发布。

## 远端与 PR 流程

远端为 [chialecode/delta](https://github.com/chialecode/delta)，默认主分支 `main`。用户已授权将两个基础提交原样推送至 main，后续工作按一个阶段一个分支、一个 PR：本地实现/自检 → A 集中审核 → push 工作分支 → 创建 PR → 检查 CI 与 review 反馈。尚有工程阻断时创建 draft PR。main 后续只经 PR 集成。

push 前同阶段 amend 为一个提交；已推送后默认追加集中修复，不擅自 force push。新提交使用现有 Git 身份附 `Signed-off-by`；用户指定 SHA 的两个基础提交保持不变。完整本地门禁与公开内容核对后集中推送，不按工作包刷提交。

本次授权包括关联远端、基础提交 push、后续阶段分支 push 和创建 PR/审核；不自动包含 PR 合并、发布、强推、仓库保护或付费集成配置。远端实际检查通过与本地技术审核、产品验收分别记录；不伪造独立审批，也不为通过而撤销保护。当前授权正本见 USER-ACTIONS 的 ACT-04。
