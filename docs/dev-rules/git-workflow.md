# Git 初始化、阶段提交与 amend

## 初始历史

用户要求首个提交只包含 **零字节 README.md**，第二个提交保存文档框架，之后单独保存技术比较与首轮计划。本次另授权清理第二提交中的已撤回技术方案并重写后续计划提交；第一个提交保持不变。无需再次初始化仓库。

默认本地 main，实施使用相容任务分支。Git 身份复用环境有效身份，不伪造作者。后续不自行重写已经结束的其他阶段；用户新授权优先。

## 一个阶段一个可审核提交

用户 D-09 明确要求：一个阶段尽可能只保留一个 commit；push 前 Agent B 的实现、Agent A 的审核修正和 B 的返工**直接 amend 该阶段提交**，不把错误实现、逐问题修复或沟通轮次保存为独立提交。阶段是计划中声明的里程碑，不等于每个 W 工作包；原 R1 的 W00～W11 仅为历史编号。

A 在文档框架之后建立当前阶段提交，起初保存该阶段计划。push 前 B 将实现直接 amend 进这个阶段提交，A 审核修正与 B 返工继续沿用；未推送时不为计划、实现或审核角色分别增加提交；已推送后的修复使用追加提交。不得 amend 文档框架提交。同阶段使用 `git commit --amend --no-edit` 或更新成描述最终状态的消息。阶段关闭且开始下一阶段后，新建下一阶段 commit。需要纠正已关闭阶段时，先确定受影响下游和当前授权，不能误 amend 另一阶段。

日常保存依靠工作区与本地备份；确有 checkpoint 提交时，在交付前合并回该阶段一个 commit。默认不创建 fixup/返工提交留在最终分支历史。报告保留 F 编号、错误触发、修复说明和验证事实；精简 Git 历史不等于伪造当时通过或删除审查证据。

## amend 前后与交接

1. 检查当前分支、HEAD、工作区归属和阶段父提交，确认 HEAD 就是当前阶段提交；尚无该阶段提交时才正常 commit；已有且未推送的该阶段计划提交则 amend；已推送后追加集中修复。
2. 比较交接的旧 SHA 与现场新 SHA/树差异，保留对方已完成修改；不能因 amend 导致 SHA 变化就退回旧版本。默认同一工作区单写入者。
3. 只暂存归属明确的本阶段文件；运行受影响检查和 `git diff --check`，核对 `git diff --cached --stat`，避免 `git add .` 混入他人文件。
4. amend 后检查父提交不变、阶段提交数量符合计划、工作区剩余改动归属明确。最终消息必须给出**新的完整 SHA**和对方 prompt；旧 SHA 失效，使用更新后的 prompt。
5. 报告记录稳定的阶段 ID、计划版本、阶段父提交、测试源码指纹、F 问题处理及证据；最终包含报告本身的 SHA 在消息中给出，避免反复自引用 amend。被测内容变化后补必要验证，不能把旧 SHA 的测试无条件套到新树。

当前授权覆盖本地阶段历史整理与阶段计划/实现/审核合并，无需每轮询问是否 amend。若存在未知下游、他人分支依赖或同时写入，先核对并隔离，不覆盖他人工作。已经发布的历史不能仅凭本规则强推；push、PR、合并、tag、发布及强推均按用户对具体外部动作的已有授权执行。

未选择项目许可证不阻塞本地开发；对外分发前处理集中台账。历史重写前可保存忽略目录下的恢复包；恢复包不是当前交付历史，不对外发布。

当前交付为 M0 v1.0（已审核的工程基础与最小桌面闭环）；完整 M1/P0 收口仍为后续 M1，见当前计划。文档框架父提交保持 `a1180cfb5f0a0051c1fc3f14ac4db7d8f06691fe`。已推送分支名 `codex/r1-workbench` 保留用于 PR #1，是历史名称，不定义阶段；不为改名强推或另建 PR。

## 远端动作与明确授权

远端为 [chialecode/delta](https://github.com/chialecode/delta)，主分支 `main`。正常流程是本地实现/自检 → A 集中审核收敛 → 在 USER-ACTIONS 登记具体阶段、提交范围、分支与拟执行动作 → 用户明确授权 → 执行该范围的 push / PR。push、PR、合并、发布各自遵守授权，不能相互推导。已明确授权的同一范围无需逐命令重复询问；新阶段、新动作或超出原范围重新确认。

“按 push/PR 流程进行”、提供远端地址、允许本地开发、测试通过、人工检查尚未做，以及使用 draft，都不能作为外部动作授权。Agent 侧阶段完成指必要自动检查通过、A 审查收敛、没有范围内阻断；人工检查和非阻塞决定可以保持 not-run，但必须如实记录。未完成阶段只有用户明确批准的具体例外才可推送/创建 PR。没有授权时继续本地实现、修复、检查与可审核版本保存，不提前执行外部操作。

一个阶段一个分支、一个 PR。push 前同阶段 amend 为一个提交；已 push 后追加集中修复，不自行 amend/force push 共享历史，最终经 squash 集成为一个阶段提交。新提交用现有 Git 身份附 Signed-off-by；两个指定基础提交的 SHA 保持不变。不使用 --all、--mirror 或删除分支来代替范围清楚的操作。本次 PR #1 特例和后续限制只在 ACT-04 维护。

## main 分支保护与合并设置

[main ruleset](../../.github/rulesets/main.json)和[仓库合并设置](../../.github/repository-settings.json)是可审查的期望配置；远端才是实际执行方。2026-10-07 已实际应用并复核 [main-protection](https://github.com/chialecode/delta/rules/24631732)，不是仅保存 JSON。

| 约束 | 当前实际配置 |
| --- | --- |
| main 更新入口 | 必须 PR；无 bypass actor，当前维护者也不能绕过 |
| 删除、强推、历史 | 禁止删除 main、禁止非快进更新，要求线性历史 |
| 审批与讨论 | 审批人数 0（单人维护，不要求自批）；不强制 code owner/最后推送人审批；review threads 必须解决 |
| 必需检查 | `docs`，绑定 GitHub Actions App 15368；该检查已真实运行成功 |
| 与 main 同步 | 不强制每次更新至最新 main；相关契约/迁移变化仍须复验 |
| 合并 | 仅 squash，PR 标题/正文形成合并消息；禁止 merge commit、rebase merge；auto-merge 关闭 |
| 分支清理 | 经授权合并后自动删除任务分支；不自动删除尚未合并的分支 |
| Actions 令牌 | 已核对默认只读、不能批准 PR；本次未改变已符合的设置 |

`DCO` 已真实成功，但不在当前 ruleset 的 required checks 中；不把没有建立的 Rust CI 说成受保护的检查。现有 docs.yml 只做文档门禁，Rust/Windows 产品验证继续按本地质量门禁。将来扩展 CI 应先产生真实成功检查再改 required context，不照搬其他仓库专用名称、不为通过检查关闭保护。

main ruleset 约束主分支集成，不能替用户审批任务分支 push，也不能阻止有权限账户创建 PR。明确授权仍是 Agent 必须遵守的独立条件。仓库保护、Actions allowlist/App、付费服务或其他安全设置的变更按具体维护授权执行，不从代码 push 授权推导。
