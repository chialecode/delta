# Agent A / Agent B 连续开发与交接

本流程适用于程序员与 AI。每轮目标是一个可运行的完整结果；不按小工作包反复征求继续。A/B 是职责分工，不自动授权创建会话或启动并行 Agent。

用户沟通与编号见 [沟通协议](communication-protocol.md)，参考及未跟踪文件见 [本地资料](local-files-and-references.md)。需要用户的事只维护 [USER-ACTIONS](../../USER-ACTIONS.md)，本流程的“集中事项”对用户事项仅作入口引用。

## 1. 角色与交接状态

| 环节 | 责任 | 输出与结束条件 |
| --- | --- | --- |
| A 计划 | 核对基线/决定，先调研开源，比较技术与通用栈，设计整合和失败边界 | 一份可执行长计划、验收映射、依赖分支、集中事项、A→B prompt |
| B 实现 | 核对现场，连续实现全部可执行工作包、自检和修复，更新受影响正本 | 交付版本、一份结果报告、命令/样本/证据、B→A prompt |
| A 审核 | 对照同一计划、代码和实证，复验高风险与变化部分；直接修局部确定问题 | 审核报告、阶段结论、集中用户事项；大缺口才整批返工 |
| 用户决定 | 产品取舍、必要实机/真实服务和外部动作 | A 回写有效决定，B/A 继续依赖部分，不重复询问 |

计划状态为 `planned → executing → ready-for-review → reviewed`；需要返工用 `changes-requested`；完成后 `closed`。这些状态与阶段验收、文档 active 无等价关系。当前值只在 [status](../delivery/status.md)维护。

## 2. 长计划必须包含

同一业务闭环内尽量长：环境与基线、开源依据、确定方案/候选区别、模块契约、依赖顺序、每包正常/失败路径、验收 ID、输出和可执行检查、降级条件、不得缩减项、真正人工依赖与结束标准。技术 spike 通过后按既定分支继续 MVP，实现细节由 B 决定；不要求做完每个 spike 再回 A。

长计划不等于一次建设所有未来基础设施。先完成当前基本功能；M2/M3 基本训练和策略贯通后再增强，循环中只带有明确价值和承接人的事项。计划命令区分“已存在”和“B 待建立”。

## 3. 连续执行与集中处理

已授权开发覆盖常规本地实现、已选依赖安装、自测修复、文档同步和明确归属的本地版本保存。先做所有不依赖缺失决定的工作；配置/人工验证记 [用户待办](../../USER-ACTIONS.md)，开源和开发缺口记 [工程台账](../decisions/open-questions.md)。

只有会改变产品范围/金融语义/权限、覆盖他人工作或产生不可逆结果且无法隔离的缺失决定，才暂停受影响部分。真实模型未配置可使用受控服务完成协议、权限与恢复测试，但真实调用保持 not-run；GPUI 失败不阻断领域/存储/AI 能力开发。不得把开发缺代码交给用户人工测试。

已给出的授权持续有效；普通进度汇报不变成审批节点。外部操作依据 [Git 规则](git-workflow.md)及当前会话，不因模板状态而多设审批。

## 4. 仓库是沟通载体

每轮一份计划、一份 B 报告、一份 A 审核（或明确独立的审核章节），复用 [交接模板](../templates/agent-handoff.md)。提示词仅给角色、入口、基线、范围、检查与交付要求，不复制另一套验收。

push 前同一阶段从计划到实现/审核尽量一个 commit：A 建阶段计划提交，B 实现、A 局部修正与 B 返工直接 amend；已 push 后默认追加集中修复，规则见 [Git](git-workflow.md)。错误实现不单列历史，但审核问题与实际修复证据保留文档。交接含计划版本、阶段父提交（R1 为文档框架）、分支、测试基点/源码指纹、未提交变更归属、amend 后新的完整 commit、证据和待处理 ID。包含报告自身的最终 commit 在聊天给出，报告使用测试基点与源码指纹；无需为了把自己的 hash 写回自身再造一次提交。

默认同一工作区只有一名写入者；用户要并行时才明确分工和隔离。B 开始发现基点不同先比较差异；可以兼容的继续，不能仅因 hash 变化或有脏文件而停工。

## 5. 自审、审核与返工

B 交付前核实所有包：代码存在、完整流程和关键失败可运行、数据/权限/恢复有证据、文档同步、必要检查通过。按“任务/需求 → 实现位置 → 验证 → 状态/限制”报告，尚未实现的必须项保持 failed/blocked，不能宣称完成。

A 检查实现并复用有效证据，不无条件全量重跑；局部修复直接处理并复验。跨模块大量编码缺口使用一次完整 `F-xx` 清单交回，含复现、预期、位置、验收和必须保留的 A 修复。B 按原编号回应，A 核实后关闭。纯风格或可隔离小改进进入 LOOP，不制造来回。

工程自检、A 技术审核、产品验收分别判断。当前必须的数据、金额、权限与恢复问题不能降级成“后续优化”。

## 6. 每次完成必须给对方 prompt

| 完成角色 | 首选下一步和 prompt 内容 |
| --- | --- |
| A 计划完成 | 给 B：仓库、唯一计划、基线/分支、连续执行范围、检查、报告与回传要求 |
| B 交付完成 | 给 A：交付 commit、报告、原计划、未完成项、需要重点核实的边界 |
| A 整批返工 | 给 B：当前版本、F 编号全集、A 已修复内容、定向复验与交付要求 |
| A 审核通过 | 给用户集中人工清单；给下一轮 B 的 prompt 只有在 A 已完成该轮计划时才提供 |

prompt 必须可以脱离聊天直接使用。用户复制 prompt 才委派对应下一任务；本轮 A 不把计划写好描述成 B 已执行。结束消息同时给结果、版本、验证、限制和一个明确推荐步骤。
