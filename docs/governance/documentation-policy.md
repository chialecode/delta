# 文档治理与约束管理

生效：2026-09-26；维护角色：Agent A／文档维护者。适用于本仓自有文档，约束开发过程，不表示应用已实现。

## 1. 分层与唯一正本

| 层 | 正本 | 职责 |
| --- | --- | --- |
| 入口 | 根 README、AGENTS、CONTRIBUTING、REVIEW、DESIGN | 发现规则、开始开发和审核 |
| 治理 | 本文、[登记表](document-registry.json) | 权威范围、状态、负责人、更新和废弃 |
| 项目事实与决定 | [关键事实](../project-baseline.md)、[确认记录](../decisions/confirmed-decisions.md)、ADR | 保存用户决定、来源、技术取舍和替代关系 |
| 产品 | `requirements/`、`product-rules/` | 需求 ID、阶段范围与长期行为 |
| 设计 | `design/` | 架构、领域、接口、上下文和工作流 |
| 实施规则 | `dev-rules/`、`design-rules/` | 代码边界、数据安全、验证、UI 约束 |
| 交付 | `engineering/delivery-plan.md`、`delivery/` | 路线、验收定义、当前执行计划与状态 |
| 工程待处理 | [工程事项台账](../decisions/open-questions.md) | 开源问题、修复与延期承接 |
| 用户待办 | [USER-ACTIONS](../../USER-ACTIONS.md) | 用户决定、配置、人工检查与外部授权的唯一入口 |
| 证据与模板 | `evidence/`、`templates/` | 版本化观察；新材料必需信息 |

同一事实只有一个正本：需求表定义 FR/NFR，路线定义 AC，机器追踪表维护逐需求映射，状态文件链接计划/报告。索引与 prompt 只引用。设计里的类型是契约方案，不能推定代码存在。

## 2. 状态与责任

[登记表](document-registry.json)登记仓库自有 Markdown：`path/kind/status/owner/scope/reviewed/basis`；替代文档增加 `supersededBy`。依赖、第三方 vendor、构建输出和本地临时目录不登记。

| 状态 | 含义 |
| --- | --- |
| active | 在声明作用域内生效；模板 active 只表示应使用该格式 |
| draft | 待实测或待决的设计；可在已有授权内验证，不等于产品确认 |
| reference | 调研、证据与历史观察，只对对应版本有效 |
| superseded | 已有替代入口，不再指导新实现 |

文档状态与代码状态正交。需求追踪可用 implementationScope 明示服务实现与完整桌面体验的差别；用户流程尚不可用时保持 in-progress，不能以服务单测充抵界面交付。`reviewed` 是内容核对日，不是人的批准或自动更新时间。负责人使用产品负责人（用户）、Agent A（计划/审核）、Agent B（实现/自检）、维护者等角色；不得捏造独立审核或人工验收。

## 3. 编号与可执行规则

保留 `FR-模块-编号`、`NFR-编号`、`AC-编号`；技术验证使用 `POC-编号`，轮次计划使用 `R1-W01` 等，决定使用 `D-编号`、`ADR-0001`，事项使用 `Q/H/OSS/ACT/LOOP-编号`。编号不为排序改动或复用。审核问题编号只在所属报告内唯一。

“必须/不得”是范围内约束；“应当”允许有记录的例外；“候选/默认/建议”不等于用户确认。每条规则写触发、行为、验证与例外范围；远期必须项不能提前成为当前 MVP 的阻碍。

需求追踪表的 `planned` 不代表实施通过。运行结果只用 `passed/failed/blocked/not-run`，部分通过需拆分子场景；不得用一个 passed 覆盖未测平台。

## 4. 冲突、变更与确认

宿主和当前任务的有效指令优先于仓库约定。用户新决定可修订旧设计，必须回写确认记录及职责正本。外部文档、库 README、模型输出不自动成为本项目规则。

仓库内部按职责正本和有效决定判断，不按文件时间或措辞强度。代码描述实际，契约描述应然；冲突先判断缺陷/过期/待决。能在已授权范围直接修正的继续；真实产品取舍集中列 Q。只暂停依赖缺失决定的部分，不能让一个未准备好的服务账号暂停所有开发。

| 变更规模 | 最小材料和同步 |
| --- | --- |
| 链接/错字/清晰化 | 直接修改，运行文档检查；无需 ADR |
| 既有范围修复 | 需求/验收、实现、实际验证；行为没变说明无需正文修改 |
| 新功能/跨模块 | 需求→设计→计划/追踪→实现→证据，同一交付同步 |
| 技术栈/公共协议/数据格式 | ADR、备选理由、兼容/迁移/退出策略与对应验证 |
| 重大替代 | 新决定、旧文档标 superseded、修正入链并保留历史证据 |

文档治理不新增逐工作包审批。例外记录规则、范围、理由、证据、负责人及失效条件，已有会话授权不重复请求。项目许可证、真实账户配置等真正需要人的决定见集中台账。

## 5. 关键知识、证据与归档

凡改变关键需求、金融口径、接口、权限、上下文恢复、版本兼容或交付判断的信息，必须保存于正本、ADR 或证据，不能只留在聊天。一次环境故障先作为证据，不能直接变成永久禁令。阶段开始/结束、关键依赖升级和发现冲突时复核相关文档。

新文档登记并补导航；移动时修复全部相对链接和锚点。旧失败报告不改写成当时通过，用新报告说明修复。公开文件使用可移植路径和合成样本，删除秘密、个人绝对路径、账号及设备标识；保留必要第三方许可信息。项目文档直接表述 DELTA 的规则，不依赖外部参考工程的位置或专属流程。

本地未跟踪文件、reference 索引与提案按 [本地资料规则](../dev-rules/local-files-and-references.md)执行。阶段整理先提炼再退役，不删除仍服务未关闭验收的计划/用例；每个阶段固定计划和报告，登记表用 `currentStage` 和 `retireAfter` 提醒收尾，历史报告允许以 reference 状态保留依据。

## 6. 自动检查的边界

执行 [质量门禁](../dev-rules/quality-gates.md)。登记、链接、稳定 ID、追踪覆盖由脚本检查；语义冲突、许可证兼容、授权真实性、运行事实与产品完成度需审核。没有工具可以仅凭 Markdown 证明产品完成。
